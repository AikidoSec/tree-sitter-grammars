================================================================================
[gap] generic type used as a value for static member access
:skip
================================================================================

Module M
	Sub Main()
		Dim x = ConsList(Of TypeSymbol).Empty
	End Sub
End Module

--------------------------------------------------------------------------------

; known grammar bug, accepted as-is — not a fix target. `member_access`'s
; `object` field only accepts `expression`, which has no alternative for
; "namespace_name + type_argument_list" the way `type` does, so a generic
; type used as a value (e.g. accessing a static member on it, as above)
; produces an ERROR on the `(Of TypeSymbol)` fragment. Two fix attempts
; (adding generic_type to expression's choices; adding an optional
; type_argument_list to member_access directly) both cascaded into new
; grammar conflicts with element_access/unary_expression/binary_expression
; — see progress.md's "Attempted and reverted" section for the full story.
;
; Confirmed the ERROR is fully self-contained and never cascades: in both
; a standalone statement and the original real-world repro
; (`New BasesBeingResolved(If(a, ConsList(Of T).Empty).Prepend(x), b)`),
; every sibling statement, the enclosing function declaration, and every
; *call* around the broken fragment — including `.Prepend(x)` chained
; directly onto its result — still parse correctly. `Type(Of T).Member`
; isn't a call at all (it's a static property/field access), so it was
; never something autotriage's call-graph extraction would track anyway;
; the only casualty is the type argument inside that one access, which
; only matters for type inference — out of scope for autotriage.
;
; Kept here (marked :skip, not deleted) as a live repro and a marker that
; this was investigated and knowingly deprioritized, not overlooked.
; Skipped tests don't count toward pass/fail (see `tree-sitter test`
; output: total excludes this one entirely) so CI stays green.
;
; Later corpus-wide measurement, which confirms the call above rather than
; overturning it. This is the *largest single cluster* of first-error causes
; among failing production files in dotnet/roslyn (19 files, where nearly
; every other distinct cause appears once), and the construct is common:
; `ArrayBuilder(Of T).GetInstance()`, `ImmutableArray(Of T).Empty`,
; `CompoundUseSiteInfo(Of T).Discarded`. So it is not rare — it is just
; genuinely harmless: re-checked through autotriage's own extractor, and
; `ArrayBuilder(Of Node).GetInstance()` still yields the call `GetInstance`,
; identical to the non-generic `ArrayBuilder.GetInstance()` control, with
; sibling, outer and chained calls all intact. Frequency is the reason to
; revisit it if the grammar is ever wanted for type inference; it is not a
; reason to revisit it for call extraction.
(source_file)

Class C
	Function F(<Out> ByRef a As Integer) As Integer
	End Function
	Function G(<[In], Out> ByRef useSiteInfo As CompoundUseSiteInfo(Of AssemblySymbol)) As Integer
	End Function
	Function H() As <Out> Integer
	End Function
	<Obsolete> Sub S()
	End Sub
End Class

--------------------------------------------------------------------------------

; FIX TARGET (unlike the generic-type gap above, which is accepted as-is).
;
; `attribute_block` ends with a mandatory `$._terminator`, and
; `_terminator: choice($._newline, ':')` — so an attribute only parses when it
; sits on its own line. Every inline position therefore fails with a MISSING
; ':' right after the closing '>':
;   - on a parameter:    Function F(<Out> ByRef a As Integer)
;   - on a return type:  Function H() As <Out> Integer
;   - same-line member:  <Obsolete> Sub S()
; `parameter` already lists `optional($.attribute_block)`, so the rule was
; meant to work; the trailing terminator is what blocks it.
;
; Not about the attribute's contents and not about line continuation:
; `<Out>`, `<[In]>` and `<Foo, Bar>` all fail identically, while a multi-line
; parameter list with no attributes parses fine. Own-line attributes on a class
; or method keep working (pinned in declarations.txt).
;
; ~3,750 occurrences across dotnet/roslyn's VB sources.
;
; Intended fix: lift `$._terminator` out of `attribute_block` and have the
; member-level position consume it instead. On fixing, replace this with
; positive cases in declarations.txt and delete the entry here.

================================================================================
[gap] null-conditional access (?. and ?())
:skip
================================================================================

Class C
	Sub S(a As Foo, x As Object)
		Dim r = a?.B
		Dim s = a?.B()
		Dim t = a?.B?.C
		Dim u = a?.B.C
		Dim v = a?(0)
		a?.B()
	End Sub
End Class

--------------------------------------------------------------------------------

; FIX TARGET (low priority — see "costs" below).
;
; `member_access` is `prec.left(10, seq(field('object', $.expression), '.',
; field('member', $.identifier)))` and there is no `?.` alternative, nor a
; null-conditional form of `element_access` for `a?(0)`. Every shape above
; fails. `?` is not used as a token anywhere else in the grammar today.
;
; ~1,995 occurrences across 277 files in dotnet/roslyn's VB sources.
;
; Costs autotriage nothing measurable: `a?.Save(n)` still yields the call
; `Save` with `object="a"`, `arity=1`, `callType=directly` — byte-identical to
; the `a.Save(n)` control — and sibling calls are unaffected. So this is parse
; hygiene, not recall.
;
; Intended fix: add `?.` (and `?(`) alternatives to `member_access` /
; `element_access`. Watch for interaction with a future nullable-type suffix
; (`Integer?`), which is also unsupported and would want the same `?` token.

================================================================================
[gap] TypeOf ... Is / IsNot
:skip
================================================================================

Class C
	Sub S(x As Object)
		Dim r = TypeOf x Is Foo
		Dim s = TypeOf x IsNot Foo
		If TypeOf x Is Foo Then
		End If
	End Sub
End Class

--------------------------------------------------------------------------------

; FIX TARGET (low priority — see "costs" below).
;
; `TypeOf` appears only as an entry in the binary-operator precedence table
; (`[1, kw('TypeOf')]`, commented "treated separately if needed") — that entry
; makes it a *binary* operator, which is the wrong shape: the right-hand side
; is a type, not an expression, and the operator is the two-token
; `Is`/`IsNot`. There is no rule for the real form, so all three fail.
;
; ~2,547 occurrences across 485 files in dotnet/roslyn's VB sources.
;
; Costs autotriage nothing measurable: calls in and around the construct are
; still extracted (a following `DoWork(1)` survives). It does add two spurious
; zero-arg call candidates, `TypeOf` and the type name, which `isSameCall`
; then filters on class/arity — noise, not error.
;
; Intended fix: a dedicated rule,
; `seq(kw('TypeOf'), $.expression, choice(kw('Is'), kw('IsNot')), $.type)`,
; and drop the misleading operator-table entry. Fairly self-contained.

================================================================================
[gap] tuple types and tuple literals
:skip
================================================================================

Class C
	Function F() As (Integer, Integer)
	End Function
	Function G() As Object
		Return (1, 2)
	End Function
	Sub S()
		Dim t As (Integer, String)
		Dim u As (k As Integer, v As String)
	End Sub
End Class

--------------------------------------------------------------------------------

; FIX TARGET (low priority — see "costs" below).
;
; `type` has no tuple alternative, and there is no tuple-literal expression,
; so both the type positions and `Return (1, 2)` fail. Named tuple elements
; (`(k As Integer, v As String)`) are a further variant of the same gap.
;
; ~1,295 occurrences across 90 files in dotnet/roslyn's VB sources — the most
; concentrated of the four, so a handful of files account for most of it.
;
; Costs autotriage nothing measurable: a following `DoWork(1)` still extracts.
;
; Intended fix: a tuple alternative on `type`, plus a tuple literal on
; `expression`. Expect this to be the fiddliest of the three: `(` after `As`
; already has to serve `type_argument_list` (`(Of T)`) and
; `array_rank_specifier` (`()`, `(,)`), and that ambiguity already needs the
; declared `[$.type, $.array_type]` and `[$._new_type, $._new_generic_type]`
; conflicts. A tuple literal additionally overlaps
; `parenthesized_expression` — `(1)` vs `(1, 2)` differ only past the comma.
